# Native Keychain custody preparation

This is v0.7 preparation, not an activated credential workflow. No real Keychain item, real signing key, public signature/broadcast, hosted secret or account was created or read during development. Tests use the fixed public scalar `1` in an in-memory fake backend. The native helper compiled and its memory-only self-test ran; actual Keychain ACL/storage compatibility has **not** been exercised. The Node private-channel and intentional-stdio-alias self-test also ran without Security APIs. Native activation requires a separate, specific authorization and an approved key source/handoff.

The only services are `org.mote.ethereum-sepolia.quote.v1` (role `quote-backup`) and `org.mote.ethereum-sepolia.bootstrap.v1` (role `bootstrap`), bound to Ethereum Sepolia 11155111. Service/account/role/access metadata must match exactly. There is no arbitrary label, chain, update, overwrite, delete, search, export-to-file, wallet-generation or all-applications option. An existing service or label makes creation fail. Quote backup is a custody backup only: the public Node interface exposes its address, not a transaction signer or a raw-key getter.

The bootstrap signer accepts exactly five ordered unsigned type-2 intents supplied by the reviewed bootstrap plan. Nonces must be consecutive. The ordered operations are three zero-value contract creations, one zero-value funding call and one bounded native allocation. It rejects unknown fields, nonempty access lists, other chains/types, changed destinations/calldata, gas above the respective 5 million / 7 million / 5 million / 250,000 / 250,000 ceilings, max fee over 2 gwei, priority fee over 1 gwei, more than one nonzero native transfer, a transfer above 0.007 test ETH, and a combined value-plus-gas ceiling above 0.05 test ETH. The one allocation must have empty calldata and an explicit recipient. The bootstrap runner additionally binds purpose, addresses, nonce ordering, bytecode/config hashes and full approval. This custody wrapper is **not** an independent durable spending authority: the runner must hold its existing exclusive lifetime journal gate and persist the exact intent before invoking the signer. Another process or a newly constructed wrapper does not inherit a safe replay decision automatically.

## Interface and secret transport

`src/keychain-custody.mjs` exports `openKeychainSigner`, `provisionFreshKeychainRole` and `handoffQuoteToRender`; none is a public secret-taking CLI. They have no default native activation. `openKeychainSigner` returns an opaque object with `getAddress()` and, for bootstrap only, `signTransaction(exactIntent)`. It never has a provider or broadcast method. The caller must supply explicit `activation: KEYCHAIN_ACTIVATION`, chain/role, absolute reviewed `helperPath` and `expectedHelperSha256`; bootstrap also requires `allowedTransactions`. The wrapper refuses native access under Node's test context, on other platforms, through symlinks, from writable-by-others helper locations, or with a mismatched helper digest. No secret is accepted via arguments or environment. The activation constant is a deliberate programming gate, not proof of user consent or a substitute for the separately approved custody operation.

The native executable accepts only `--activate-native-keychain-v1`, `--self-test` or the non-Keychain `--self-test-private-channels` descriptor check. Activation metadata goes through stdin. Exactly 32 private bytes for provisioning use **FD 3**; internal reads return exactly 32 bytes through **FD 4**. Both must be distinct nonterminal pipes/sockets, never regular files or aliases of stdin/stdout/stderr. stdout carries only fixed nonsecret success/refusal JSON; stderr carries nothing. The Node wrapper never forwards child diagnostics and rejects unexpected output, timeouts or oversized data. Child environment is reduced to PATH/LANG. No `security -w`, shell interpolation or command-line key transport is used.

The helper opens only the existing `~/Library/Keychains/login.keychain-db`, requiring a regular owner-only file, current-user ownership, no symlink and an unlocked keychain. It neither creates nor unlocks a keychain. All searches are restricted to this handle and writes explicitly target it, with no default-search-list fallback. It disables interactive Keychain prompts, constructs application-specific ACLs for its own executable and inspects those ACLs before reading data. Any ACL with a wildcard, missing application list, additional application, nonzero prompt selector or changed description fails closed. This validates the application list and prompt/description; it is not a complete audit of authorization tags or owner/partition semantics. The SDK explicitly allows default ACL configurations to change between releases, so no invented authorization-tag whitelist is used. It uses classic macOS Security Keychain ACL APIs; the current SDK marks these APIs deprecated. This deliberate restriction may reject a platform-generated ACL. **Compilation is not proof that a real item can be created/read unattended.** Do not weaken ACL checks, allow all applications, or enable UI as an automatic fallback. A separately authorized real compatibility test is still required before claiming native custody is operational.

The native helper should be built once in an approved owner-only directory, pinned by SHA-256, and kept at its reviewed path. Changing/rebuilding the helper can change its trusted-application identity and require a separately reviewed custody migration; there is no automatic reauthorization. Generic-password custody is exportable to the authorized helper, not Secure Enclave or hardware-wallet custody. Private bytes necessarily enter helper/Node process memory for signing; buffers are cleared where practical, but JavaScript strings, copies and garbage collection prevent a complete memory-erasure guarantee. The helper digest is checked before process creation, not through an atomic OS executable handle; same-user replacement between that check and execution is outside this threat model. A compromised same-user process or host is outside this boundary.

If a create operation times out or post-create ACL verification fails, its outcome may be **uncertain**: retain the state and reconcile the exact item through an approved native procedure. Never retry blindly, delete a possibly created item, change its label or create replacement authority. Read failures also stop; no fallback file, fixture, wallet or key is selected.

## Compile and non-Keychain tests

Compile to a **new** path with `node scripts/keychain/build.mjs --out /absolute/new/helper-path`. The build script does not execute the helper or call Keychain. The resulting digest is public review metadata, not a credential. The compiler needs an existing macOS SDK and may emit legacy API warnings.

Running that binary with `--self-test` exercises only memory/request validation and reports `keychainCalls:0`. The separate `--self-test-private-channels` mode, launched with five Node pipe descriptors and no key bytes, verifies pipe/socket separation and rejects an intentional stdout alias. This passed on the inspected macOS/Node 24 environment; other platform versions remain unverified. Unknown arguments fail before Security APIs. `node --test test/keychain-custody.test.mjs` exercises only the explicit fixture backend and native activation refusal. No real backend is selected by default, no test creates credentials and no secret is printed. Do not run the native activation flag as a test.

`provisionFreshKeychainRole` validates role, chain, explicit activation and the native helper before touching the CSPRNG. It then permits at most four attempts to produce a valid secp256k1 scalar, sends the bytes only through the private helper pipe, and returns the public address and creation status. Tests never enter that branch. The raw-byte provisioning routine is module-private, so no human must copy a private key into chat, argv or a configuration file.

`describeQuoteHandoff` prepares public review metadata. `handoffQuoteToRender` requires the quote-backup role and an independently reviewed descriptor hash binding the exact Render service ID, canonical `https://<name>.onrender.com` origin, deployment config hash, quote-signer address, network, Keychain service and the sole permitted environment-key name. A trusted in-memory sink must identify that same hash. The wrapper checks the stored key's public address before passing 32 private bytes to the sink, returns only public receipt metadata and clears its buffer afterward. Native options, target and callback are captured before asynchronous work so caller mutation cannot switch custody roles or destinations. A thrown or ambiguous sink result reports outcome unknown and must be reconciled without automatic retransmission.

The callback is an explicitly trusted integration boundary: JavaScript cannot stop it copying/logging bytes, forwarding them elsewhere or lying about remote acceptance. Actual sink implementation, destination and credential transfer require separate review/authorization; the fake sink used here has no network or browser operation. No actual Render target was invented, accessed or provisioned.

Quote-key handoff activation to an approved hosting secret manager remains separate. This candidate has no browser-secret automation and no stdout/env/file export command. Bootstrap custody and the controlled payer must remain distinct; all quote/deployer/merchant/payer bindings are checked by the outer deployment policy. Ongoing calls can be unattended only after valid provisioning, native access compatibility, exact policy and durable authority are established.
