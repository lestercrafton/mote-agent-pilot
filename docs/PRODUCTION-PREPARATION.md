# Mote v0.8.5-production-prep.1

Local release candidate, November 1, 2026. Payments remain disabled. This is not a production launch or an authorization to provision keys, deploy, accept payments, or spend money.

## What changed

- Combined v0.8.1 HTTP/startup/SQLite integration with the byte-identical v0.8.4 bounded log-recovery patch. The strict payment verifier, protocol, service state machine, client, journal schema and backup validator are unchanged.
- Added a separate native-USDC-on-Base profile for `/v1/usdc/audit`. Its proposal is 10,000 base units (0.01 USDC), at most 100 lifetime settlement attempts, within one fixed interval no longer than 24 hours. Expired or failed attempts still consume the cap; restarting never resets it. The interval is bound into the configuration/journal identity. Renewing it requires review and an explicit migration, not a fresh empty database.
- New production admission is gated on disk/WAL checks and a successful recent SQLite-consistent backup. Startup takes a fresh quarantined snapshot; hourly snapshots have a 2-hour freshness limit, 26-copy count limit and 256 MiB accounting limit. No automatic deletion, off-host transfer or restore activation. Interruptions retain partial files and block further backup/admission until reviewed. Existing payments can recover when admission is stopped.
- Added an unfunded durable receipt/offer signer provisioner, never called by startup. It reserves public intent before writing any key; every existing or interrupted item prohibits another identity. The runtime exposes only `address` and `signMessage`. Public scalar fixtures cover exceptions and actual SIGKILL at intent/key/installed checkpoints. No real identity was created.
- Added an explicit old-to-new source authorization adapter for the existing testnet quote key. All 86 legacy files remain unchanged. The adapter retains the original custody code with one explicit source-authorization check and adjusted import paths. It keeps the real `RENDER_GIT_COMMIT`; it does not edit old import records, move/read the live key during preparation, repeat its import, or alter filesystem permissions. Fixture tests compare every original record byte and enforce the limited fork diff.

## Custody and data boundaries

The user-confirmed receiving address is only in `private-operator/recipient.json`, mode0600, outside the public manifest/archive. No email, residence or wallet recovery material is included. Public-source configuration uses a placeholder. The recipient can receive native USDC on Base; that does not prove a recovery backup or grant spending authority.

The proposed receipt key lives only at `/var/data/mote-usdc/production/receipt.key` on existing Render service `srv-dbijuvou01pc73d59c30`, with0700 directories and0600 single-link files. It is a real secp256k1 key despite its limited application interface: never fund it, and never use it as the revenue wallet. Host/application compromise could forge service offers/receipts and could spend any assets mistakenly sent to that key. Buffer wiping is best effort; JavaScript strings cannot be guaranteed erased.

Existing CDP credential remains `/var/data/mote-usdc/cdp.json`, with existing permissions and IP restrictions. The new runtime requires an independently recorded hash of its public API-key ID before using it. No CDP wallet secret, user receiving-wallet key, testnet bootstrap key or payer key is needed. No secrets should enter shell arguments, terminal output, screenshots, chat, source, environment variables, or logs. The separate native provisioner emits only public identity/status. No key leaves Render in this proposal.

Database backups contain results, payer public addresses and signed authorizations. They remain private on the same disk and always restore quarantined. This protects process restart and logical recovery; it is **not** an off-host disaster backup. Disk loss can lose both receipt signer and records. A public beta must disclose that limitation; off-host export remains disabled and needs a separately approved destination. No automatic refund, signer rotation, reauthorization of uncertain payments or rollback of spent counters is allowed.

Payers must use EOA EIP-3009 signatures and the Mote request-binding helper. Arbitrary x402 clients and smart-wallet payers are not supported by this profile. A smart-wallet revenue recipient is different and can receive the token transfer. Inputs must be public synthetic data; no secrets. HTTP200 `/ready` means recovery service is available; inspect `usdc.newAdmissionAllowed` for admission. `productionReady:false` deliberately makes no broad assurance.
